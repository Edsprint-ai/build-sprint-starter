## What you are building

A computer system wrote tens of thousands of log lines overnight. Somewhere in
there are real problems, hidden among a lot of normal noise.

Your tool reads the log file and answers one question:

> **What should I look at first, and which lines prove it?**

**Who it is for:** an on-call engineer with a large log file and twenty minutes.

**What it returns:** up to five problems ("findings"), most important first.
Each finding lists the log lines it is based on. Return fewer than five if
there are fewer real problems. Five weak findings score worse than three good
ones.

**The hard part:** normal activity is noisier than the real problems. Some
rare events are harmless. Looking for the word "error" does not work.

**Not in scope:** live log streaming, user accounts, alerting, other log
formats.

## The data

- **Practice log:** `fixtures/log-analyser/visible.log`. It comes with the
  answers in `fixtures/log-analyser/visible.json`, so you can check your work
  as often as you like.
- **Final test:** a different log of the same kind, which you never see. Your
  final score comes from that one. This is so your tool has to work in
  general, not only on the practice log.

The logs were generated by EdSprint from a test system with problems added at
known times. They contain no real people's data. Still follow
[docs/DATA-RULES.md](../docs/DATA-RULES.md).

The `sha256` in `visible.json` is the hash of the log text without its final
newline, so it will not match `shasum` on the file directly.

## How you check your work

Two commands:

```
pnpm analyse --input fixtures/log-analyser/visible.log --out out/findings.json
pnpm score
```

The first runs your tool on the practice log and saves the findings. The
second compares them with the answers and prints your score.

Until you write stage 3, both run but your score is zero. That is expected.

**The pass marks:**

| Measure | What it means | Needed |
|---|---|---|
| recall@5 | How many of the real problems your top five found | 0.80 |
| precision@5 | How many of your findings were real problems | 0.75 |
| grouping F1 | How well you grouped similar log lines | 0.70 |
| time | How long the final run takes, with 2 CPUs and 4 GB of memory | 60 seconds or less |

These numbers do not change during the programme. They were set by building a
simple version first, so they are reachable.

**Also required:** at least 95% of lines parsed. Count the lines you cannot
parse and show that number on screen. Never hide them.

The exact rules for the final run are in
[docs/EVALUATION-CONTRACT.md](../docs/EVALUATION-CONTRACT.md).

**Missing a pass mark does not cost you your certificate.** Your certificate is
about your own work. A squad that misses the number, says so honestly, and
explains why has done the assignment. A faked result does not pass.

## The six stages

The code is already split into these folders in `src/stages/`.

| Stage | What it does | Watch out for |
|---|---|---|
| 1 Ingest | Read the log file | Loading the whole file at once. Read it line by line |
| 2 Normalise | Turn each line into a clean record, especially the time | Silently dropping lines. Count them |
| 3 Detect | Find the problems with normal code and statistics | **No AI here.** It must work with no API key |
| 4 AI | Use Claude to explain what stage 3 found, in plain words | It explains. It never adds new findings |
| 5 Screen | One page that answers the question. Click a finding to see its lines | Nine charts. One question, one page |
| 6 Ship | Anyone can clone it and run it from the README | Only working on your own laptop |

**Stage 3 must work without AI. Stage 4 must still exist.** Your score comes
from stage 3. Stage 4 makes the result easy to read.

### Rules for the AI stage

- Check every AI response against a fixed format before using it.
- Every statement the AI makes must point to log lines.
- Log text is untrusted. Someone could hide instructions inside a log line.
  Ignore them, and show this working in your demo.
- If the AI fails (no key, timeout, bad answer), show the stage 3 result with a
  notice. Never a blank page or an error dump.
- Record tokens, time and cost for every AI call.
- Save AI responses while developing so repeat runs cost nothing. The starter
  already does this. See [docs/CLAUDE-SETUP.md](../docs/CLAUDE-SETUP.md).

## Who does what

### Product manager

- **Week 1:** the problem statement (`briefs/problem-brief.md`). One user, one
  question.
- **Week 2:** talk to two people who do on-call work, and write notes. Draw
  rough screens. Split features into must-have and nice-to-have.
- **Week 4:** run the score with the engineers and read it honestly.
- **Week 5:** cut the nice-to-haves that will not make it, in writing, with the
  date and the reason.
- **Week 6:** watch three people use the tool without help. Write down where
  they got stuck.
- **Week 7:** write the demo script.

### Engineers

- **Week 1:** split ownership between you and write it in the README:
  - stages 1 and 2 (reading and cleaning the log)
  - stage 3 (detection and the score)
  - stage 4 (the AI part)
  - stage 5 (the screen)

  Each part has one named owner. Owning something means you answer for it.
  You still help each other and review each other's code.
- **Week 1:** fill in `THIRD_PARTY.md` and `COSTS.md`.
- **Week 2:** a one-page design doc. Agree on the approach before writing code.
- Every change is a pull request that another engineer reviews.
- Test on your own machine before you push. Keep the check mark green.
